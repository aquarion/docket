# Agent notes for this repo

Notes for any AI coding agent (Claude Code, GitHub Copilot, etc.) working on
this codebase — context that isn't obvious from reading any single file.

## Calendar event date/time handling

`resources/js/date-utils.js`, `resources/js/docket-events.js`,
`resources/js/docket-calendar.js`, and `app/Services/GoogleCalendarService.php`
implement all-day/timed event bucketing and display. This area has a history
of subtle timezone and boundary bugs (see PR #249), because "is this event
all-day, and where does it actually end?" has **four independent origins**
that all have to agree:

1. A genuine ICS date-only value (`DTSTART;VALUE=DATE:...`, `isDate === true`
   on the parsed property).
2. An explicit vendor all-day flag (`x-microsoft-cdo-alldayevent` or
   `x-apple-allday` set to `"TRUE"`) on an event whose underlying
   DTSTART/DTEND are still real date-times.
3. A duration-only heuristic in `processSingleEvent` (an ordinary timed
   event that just happens to run ≥1440 minutes, no flag involved).
4. `updateNextUp`'s heuristic promotion of a timed event that started before
   today and runs past end-of-day.
5. Google Calendar's `event.start.date` (vs. `dateTime`) — always a genuine
   all-day event, no heuristic case on that side.

Only (1), (2), and (5) are genuine all-day events whose `end` is an RFC 5545
**exclusive** boundary (the day after the last day the event covers). (3) and
(4) have a real, literal end instant that covers the end day itself. This is
why events carry an explicit `exclusiveEnd` boolean set once at each event's
origin (`isExplicitAllDay()` in `docket-calendar.js`, or `event.start.date`
in `GoogleCalendarService`) — **never** infer it from `allDay` alone, and
never re-derive it from a timestamp later. The one exception:
`DateUtils.lastCoveredDay(event, end)` also treats a literal end that happens
to land exactly on local midnight as if it were exclusive, since e.g. "ends
tomorrow at 00:00" hasn't actually run into tomorrow either way.

Other traps already hit and fixed here, worth not re-introducing:

- Bare `"YYYY-MM-DD"` strings (Google all-day `start`/`end`, and day-bucket
  keys) must be parsed as **local** calendar dates via
  `DateUtils.parseEventDate()`, not `new Date(dateString)` — the latter is
  UTC per spec and shifts the date by one day for any viewer not at UTC+0.
- Day-count/day-of-year arithmetic must go through `DateUtils.buildUtcTime()`
  / `DateUtils.getDayNumber()` (UTC timestamps of local Y/M/D), not raw
  millisecond division — a local calendar day can be 23 or 25 real hours
  across a DST transition.
- `getDayNumber()` is an absolute, ever-increasing count, not a
  year-relative ordinal — needed so Dec 31 and the next Jan 1 compare as
  consecutive days.
- The `/all-calendars?end=...` request parameter is a wire contract parsed
  by the backend with `strtotime()` in UTC (Google's exclusive `timeMax`) —
  it must stay UTC (`toISOString()`), unlike every local-display date string
  elsewhere.
- `GoogleCalendarService`'s cache key includes a `schema` field specifically
  so that adding/changing a field in the cached event shape (like
  `exclusiveEnd`) can't be served stale from a pre-deploy cache entry.

Open question, never resolved: whether `DateUtils.buildUtcTime()`'s
defensive handling of `Date.UTC()`'s "years 0-99 mean 1900-1999" quirk is
worth keeping given every real input here is a four-digit calendar year.
Multiple reviews have suggested inlining it back to `Date.UTC(year, month,
day)`; ask the repo owner before doing so either way.

## Working with PRs on this repo

Comments and pushes authored under the repo owner's own GitHub account are
not necessarily typed by a human — this repo runs multiple automated
Claude-based review/fix passes (look for a
`🤖 Generated by Claude Code`-style footer) that post as that account, and
more than one Claude Code session has been observed pushing to the same PR
branch concurrently. Before pushing, fetch and check whether the remote
branch has moved; if it has, review the diff on its own merits rather than
assuming it's stale or wrong.
